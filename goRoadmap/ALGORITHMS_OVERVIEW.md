# Обзор алгоритмов, встречающихся в проекте

Проект посвящен распознаванию показаний тонометра по фотографиям. Алгоритмы в нем можно разделить на несколько уровней: подготовка изображений, локализация дисплея, уточнение геометрии, бинаризация, детекция цифр, распознавание, оценка качества и инженерные вспомогательные процедуры.

## 1. Общая карта пайплайна

Типовой путь обработки изображения в проекте:

1. Загрузка фотографии из `data/`.
2. Нормализация размера, crop или выравнивание.
3. Поиск дисплея тонометра.
4. Уточнение границы дисплея.
5. Перспективное выпрямление дисплея.
6. Бинаризация выпрямленного изображения.
7. Морфологическая очистка и соединение сегментов цифр.
8. Поиск bounding box цифр.
9. Группировка цифр по строкам.
10. Распознавание семисегментных цифр.
11. Сопоставление с эталоном и расчет метрик.

## 2. Алгоритмы подготовки и нормализации изображений

### 2.1. Resize

**Где встречается:** `crop_by_binary_white_area.ipynb`, `horizontal_image_alignment.ipynb`, `screen_digit_7seg_cv.ipynb`.

**Идея:** уменьшить изображение до заданной максимальной стороны, чтобы ускорить обработку и сделать параметры более стабильными.

**Роль в проекте:** фотографии имеют разные размеры, часть снимков очень крупные. Resize позволяет применять Canny, K-means, Hough и connected components быстрее.

**Плюсы:** ускорение, меньше расход памяти, стабильнее размеры ядер и порогов.

**Минусы:** при сильном уменьшении можно потерять тонкие сегменты цифр.

### 2.2. Center crop

**Где встречается:** `final.ipynb`, `screen_digit_7seg_cv.ipynb`.

**Идея:** взять центральную область изображения, предполагая, что тонометр находится ближе к центру.

**Роль в проекте:** ранняя попытка сократить область поиска.

**Плюсы:** просто и быстро.

**Минусы:** опасный шаг. Если экран или край прибора не попадает в crop, дальнейшие алгоритмы уже не могут восстановить потерянную область.

### 2.3. Crop by largest white area

**Где встречается:** `crop_by_binary_white_area.ipynb`.

**Идея:** сначала построить бинарную маску на полном изображении, затем найти самую большую внутреннюю белую связную область, расширить ее bbox и только после этого обрезать исходное изображение.

**Роль в проекте:** исправляет проблему раннего центрального crop из `final.ipynb`.

**Плюсы:** crop становится завязан на содержимое изображения, а не на жесткое предположение о центре.

**Минусы:** если бинарная маска ошиблась, crop тоже ошибается.

### 2.4. Автоматическое горизонтальное выравнивание

**Где встречается:** `horizontal_image_alignment.ipynb`, результаты в `aligned_data/`.

**Идея:** оценить угол наклона основного объекта и повернуть изображение без обрезания.

**Используемые подалгоритмы:**

- Hough lines для поиска доминирующих линий.
- PCA как запасной способ оценки главной оси объекта.
- `rotate_bound` для поворота без потери краев.

**Результат в проекте:** обработано 79 изображений, все со статусом `ok`, метод во всех строках `hough_lines`.

**Плюсы:** полезная предварительная нормализация, особенно когда тонометр сильно повернут.

**Минусы:** горизонтальное выравнивание не исправляет перспективу экрана. Для дисплея все равно нужен `warpPerspective`.

## 3. Классическая локализация дисплея

### 3.1. Canny edge detector

**Где встречается:** описан в PDF-отчете и обнаружен в `horizontal_image_alignment.ipynb`; как часть классического подхода к ROI.

**Идея:** найти резкие перепады яркости, то есть края объектов.

**Роль в проекте:** используется для поиска границ дисплея перед поиском контуров.

**Плюсы:** быстрый, объяснимый, не требует обучения.

**Минусы:** чувствителен к бликам, теням, шуму, слабому контрасту и размытому фокусу.

**Фактический вывод:** классическая локализация через Canny оказалась слабой для сложных снимков тонометра.

### 3.2. findContours

**Где встречается:** `final.ipynb`, `horizontal_image_alignment.ipynb`, `screen_digit_7seg_cv.ipynb`, `ssd_recognition_pipeline.ipynb`, генератор OCR-ноутбука.

**Идея:** найти замкнутые или связные границы объектов на бинарном изображении или карте краев.

**Роль в проекте:** используется для поиска границ дисплея, масок, bbox цифр и компонент после морфологии.

**Плюсы:** стандартная и быстрая OpenCV-процедура.

**Минусы:** качество полностью зависит от предварительной бинаризации или edge map.

### 3.3. approxPolyDP

**Где встречается:** `final.ipynb`, классический ROI-подход в PDF.

**Идея:** аппроксимировать сложный контур многоугольником с меньшим числом точек.

**Роль в проекте:** попытка получить четырехугольник дисплея по найденному контуру.

**Плюсы:** хорошо подходит, если границы дисплея четкие.

**Минусы:** ломается при бликах, тенях, разрывах и посторонних контурах.

**Фактический результат:** классический пайплайн Canny -> findContours -> approxPolyDP давал около `30.8%` TP без предобработки и около `35.2%` после повышения контраста.

### 3.4. Фильтрация по площади

**Где встречается:** PDF-отчет, классический ROI, digit detection.

**Идея:** отбрасывать слишком маленькие или слишком большие области.

**Роль в проекте:** уменьшает число ложных срабатываний при поиске дисплея и цифр.

**Плюсы:** простой способ убрать очевидный мусор.

**Минусы:** требует ручного подбора порогов; может удалить правильный объект при нестандартном масштабе.

## 4. Предобработка контраста и яркости

### 4.1. Histogram equalization

**Где встречается:** PDF-отчет в сравнении предобработок.

**Идея:** перераспределить яркости так, чтобы повысить общий контраст изображения.

**Роль в проекте:** проверялась перед классической локализацией дисплея.

**Вывод:** не стала лучшим методом; глобальная коррекция не всегда помогает при локальных бликах и тенях.

### 4.2. CLAHE

**Где встречается:** PDF-отчет в локализации и бинаризации.

**Идея:** локальное выравнивание гистограммы с ограничением контраста.

**Роль в проекте:** проверялась как предобработка для Otsu и для классического поиска ROI.

**Плюсы:** усиливает локальные детали.

**Минусы:** может усилить шум; при тенях Otsu после CLAHE все равно может ошибаться.

### 4.3. Linear contrast

**Где встречается:** PDF-отчет.

**Идея:** линейно усилить контраст через коэффициент `alpha`.

**Роль в проекте:** улучшала видимость границ для Canny.

**Фактический результат:** `alpha=1.5` поднял долю TP в классическом ROI примерно до `35.2%`.

### 4.4. Gamma correction

**Где встречается:** PDF-отчет.

**Идея:** нелинейно изменить яркость изображения.

**Роль в проекте:** проверялась как способ улучшить контраст дисплея и цифр.

**Плюсы:** помогает вытянуть темные или светлые зоны.

**Минусы:** один gamma-параметр плохо подходит ко всем типам освещения.

### 4.5. Bilateral filter

**Где встречается:** PDF-отчет.

**Идея:** сгладить шум, сохраняя границы.

**Роль в проекте:** проверялся перед контурным поиском и Otsu-бинаризацией.

**Плюсы:** лучше обычного blur сохраняет края.

**Минусы:** не решает проблему бликов и слабого LCD-контраста сам по себе.

### 4.6. Unsharp mask

**Где встречается:** PDF-отчет.

**Идея:** усилить резкость и края изображения.

**Роль в проекте:** проверялся как препроцессинг для Canny.

**Минусы:** вместе с полезными границами может усилить шум.

## 5. Цветовая и пиксельная сегментация

### 5.1. K-means по пикселям

**Где встречается:** `final.ipynb`, `crop_by_binary_white_area.ipynb`, `final_vs_device_border.ipynb`, `screen_digit_7seg_cv.ipynb`, `quantize_result_images.py`.

**Идея:** разделить пиксели на `k` кластеров по цвету или яркости.

**Роль в проекте:**

- сегментация изображения на светлые и темные области;
- поиск крупной области прибора или экрана;
- цветовая квантизация результатов в `quantize_result_images.py`;
- вспомогательный шаг после Otsu в `screen_digit_7seg_cv.ipynb`.

**Плюсы:** не требует разметки и обучения.

**Минусы:** не понимает семантику объектов; при бликах и тенях кластеры могут не соответствовать экрану или цифрам.

### 5.2. Цветовая квантизация

**Где встречается:** `quantize_result_images.py`.

**Идея:** уменьшить изображение до фиксированного числа цветов через K-means.

**Роль в проекте:** упрощает визуальную структуру изображений в папке результатов.

**Плюсы:** может сделать сегменты и области более читаемыми.

**Минусы:** это вспомогательная визуальная/предобрабатывающая операция, не полноценный распознаватель.

### 5.3. Connected components

**Где встречается:** `crop_by_binary_white_area.ipynb`, `final.ipynb`, `horizontal_image_alignment.ipynb`, `screen_digit_7seg_cv.ipynb`, `ssd_recognition_pipeline.ipynb`.

**Идея:** найти все связные группы пикселей на бинарной маске.

**Роль в проекте:**

- поиск самой большой внутренней области;
- удаление мелких шумовых компонент;
- выделение объектов после бинаризации.

**Плюсы:** быстрый и понятный метод.

**Минусы:** если цифры слипаются с шумом или рамкой, connected components объединяет их в один неправильный объект.

## 6. Геометрические алгоритмы

### 6.1. minAreaRect

**Где встречается:** `final.ipynb`, `horizontal_image_alignment.ipynb`, `screen_digit_7seg_cv.ipynb`, `ssd_recognition_pipeline.ipynb`.

**Идея:** построить минимальный повернутый прямоугольник вокруг контура или маски.

**Роль в проекте:** получить OBB-подобную геометрию из маски, особенно после SAM2 или контурного поиска.

**Плюсы:** хорошо описывает наклоненный прямоугольный объект.

**Минусы:** чувствителен к лишним пикселям маски.

### 6.2. Упорядочивание углов

**Где встречается:** `screen_digit_7seg_cv.ipynb`, `ssd_recognition_pipeline.ipynb`.

**Идея:** расположить четыре точки в устойчивом порядке, чтобы правильно построить перспективное преобразование.

**Роль в проекте:** перед `warpPerspective` нужно знать, где верхний левый, верхний правый, нижний правый и нижний левый углы.

**Минусы:** если исходные точки плохие или сам полигон самопересекается, порядок не спасает геометрию.

### 6.3. Perspective transform / warpPerspective

**Где встречается:** `screen_digit_7seg_cv.ipynb`, `ssd_recognition_pipeline.ipynb`.

**Идея:** преобразовать четырехугольник дисплея в прямоугольник.

**Роль в проекте:** ключевой этап между локализацией дисплея и распознаванием цифр.

**Плюсы:** убирает перспективные искажения и делает строки цифр более горизонтальными.

**Минусы:** качество полностью зависит от точности найденных углов или маски дисплея.

### 6.4. Polygon IoU

**Где встречается:** `ssd_recognition_pipeline.ipynb`.

**Идея:** сравнить два полигона через маски: пересечение делится на объединение.

**Роль в проекте:** оценка качества OBB/SAM2-локализации относительно GT.

**Плюсы:** подходит для повернутых и перспективных областей.

**Минусы:** зависит от разрешения маски и качества GT.

## 7. Нейросетевые алгоритмы локализации и сегментации

### 7.1. Базовая YOLOv8n

**Где встречается:** `boris_fast_yolov8n_rectangles.ipynb`, вес `yolov8n.pt`.

**Идея:** готовая COCO-модель ищет стандартные классы объектов.

**Роль в проекте:** быстрый эксперимент на 10 фотографиях Бориса.

**Фактический результат:** найдено 8 bbox на 5 из 10 снимков, но классы были посторонними: `person`, `book`, `tv`, `laptop`, `keyboard`, `cell phone`.

**Вывод:** базовая YOLOv8n без дообучения не решает задачу поиска дисплея тонометра.

### 7.2. Дообученная YOLOv8n bbox

**Где встречается:** PDF-отчет.

**Идея:** обучить YOLO находить дисплей как обычный прямоугольный bbox.

**Результат:** около `81%` удачных детекций без аугментации и около `87%` с аугментацией.

**Плюсы:** резко лучше классического Canny-подхода.

**Минусы:** обычный bbox плохо описывает повернутый или перспективно искаженный дисплей.

### 7.3. YOLOv8n-OBB

**Где встречается:** PDF-отчет, `ssd_recognition_pipeline.ipynb`.

**Идея:** предсказывать повернутый bounding box, а не прямоугольник по осям изображения.

**Роль в проекте:** основной нейросетевой детектор дисплея в итоговом пайплайне.

**Результаты:**

- в PDF: средний IoU около `0.958`, успешность около `89%`;
- в `ssd_recognition_pipeline.ipynb`: `%TP = 93.5%`, `mean IoU = 0.923`.

**Плюсы:** лучше соответствует геометрии наклоненного экрана.

**Минусы:** все еще не описывает настоящую перспективную форму идеально.

### 7.4. YOLOv8n-KPT / Pose

**Где встречается:** PDF-отчет.

**Идея:** находить ключевые точки, например углы дисплея.

**Роль в проекте:** эксперимент для учета перспективных искажений.

**Результат:** средний IoU около `0.824`, успешность около `76%`.

**Плюсы:** теоретически лучше подходит для четырехугольника экрана.

**Минусы:** в данном проекте оказалась слабее OBB, хотя иногда лучше справлялась со сложными бликами.

### 7.5. SAM2

**Где встречается:** PDF-отчет, `ssd_recognition_pipeline.ipynb`.

**Идея:** сегментационная модель уточняет маску объекта по подсказке от YOLO.

**Роль в проекте:** уточнение границ дисплея перед перспективным выпрямлением.

**Результаты:**

- в PDF SAM2 повышал IoU и уменьшал FP-площадь;
- в итоговом ноутбуке после SAM2 `mean IoU = 0.955`, прирост `+0.032`, но `%TP` снизился до `82.6%`.

**Плюсы:** улучшает точность границ у успешных масок.

**Минусы:** может чрезмерно уменьшить область или ошибиться, поэтому в ноутбуке есть проверка `MIN_AREA_RATIO = 0.6`.

### 7.6. Аугментация данных

**Где встречается:** PDF-отчет.

**Идея:** искусственно увеличить разнообразие train-выборки изменениями изображения.

**Роль в проекте:** улучшение обучения YOLO на маленьком датасете.

**Результат:** для обычной YOLOv8n успешность выросла примерно с `81%` до `87%`.

## 8. Бинаризация

### 8.1. Otsu thresholding

**Где встречается:** `screen_digit_7seg_cv.ipynb`, PDF-отчет.

**Идея:** автоматически выбрать глобальный порог по гистограмме яркости.

**Роль в проекте:** проверялся как базовый способ отделить цифры от фона.

**Плюсы:** не требует ручного порога.

**Минусы:** плохо работает при тенях, бликах и неравномерной яркости дисплея.

### 8.2. Adaptive Mean Threshold

**Где встречается:** `ssd_recognition_pipeline.ipynb`, PDF-отчет.

**Идея:** считать порог локально по среднему в окне вокруг пикселя.

**Роль в проекте:** основной метод бинаризации в итоговом пайплайне.

**Результаты:** базовый `AdaptiveMean_31_2` дал F1 около `0.6086`; после настройки и постобработки лучший результат доходил примерно до `0.673`.

**Плюсы:** лучше глобального Otsu при неравномерном освещении.

**Минусы:** может создавать шум на резких фотографиях.

### 8.3. Adaptive Gaussian Threshold

**Где встречается:** PDF-отчет.

**Идея:** локальный порог считается с гауссовыми весами.

**Результат:** уступил Adaptive Mean, F1 около `0.5522`.

### 8.4. CLAHE + Otsu

**Где встречается:** PDF-отчет.

**Идея:** сначала локально усилить контраст, затем применить Otsu.

**Результат:** F1 около `0.5328` в базовом сравнении.

**Вывод:** иногда хорошо выделяет цифры, но нестабилен при тенях.

### 8.5. Gaussian blur + Otsu

**Где встречается:** PDF-отчет.

**Идея:** сгладить шум перед глобальным Otsu.

**Результат:** F1 около `0.5204`.

### 8.6. Bilateral filter + Otsu

**Где встречается:** PDF-отчет.

**Идея:** сгладить шум с сохранением границ, затем применить Otsu.

**Результат:** F1 около `0.5172`.

### 8.7. Инверсия бинарной маски

**Где встречается:** `ssd_recognition_pipeline.ipynb`, `screen_digit_7seg_cv.ipynb`.

**Идея:** сделать целевые объекты белыми на черном фоне или наоборот.

**Роль в проекте:** OpenCV-морфология и connected components ожидают удобную полярность: цифры часто приводятся к белым пикселям.

## 9. Морфологические алгоритмы

### 9.1. Erosion

**Где встречается:** `ssd_recognition_pipeline.ipynb`, PDF-отчет, генератор OCR-ноутбука.

**Идея:** сужает белые области.

**Роль в проекте:** удаляет мелкий шум после бинаризации и после дилатации.

**Плюсы:** чистит мусор.

**Минусы:** может стереть тонкие части семисегментных цифр.

### 9.2. Dilation

**Где встречается:** `ssd_recognition_pipeline.ipynb`, `screen_digit_7seg_cv.ipynb`, PDF-отчет, генератор OCR-ноутбука.

**Идея:** расширяет белые области.

**Роль в проекте:** соединяет разорванные сегменты цифр, помогает получить один bbox на цифру.

**Плюсы:** полезна при разрывах сегментов.

**Минусы:** может склеить цифры с шумом или рамкой дисплея.

### 9.3. Opening

**Где встречается:** PDF-отчет как проверяемая морфологическая операция.

**Идея:** erosion -> dilation.

**Роль в проекте:** удаление мелкого шума.

### 9.4. Closing

**Где встречается:** PDF-отчет как проверяемая морфологическая операция.

**Идея:** dilation -> erosion.

**Роль в проекте:** закрытие маленьких разрывов в сегментах.

### 9.5. Удаление маленьких компонент

**Где встречается:** `ssd_recognition_pipeline.ipynb`.

**Идея:** через `connectedComponentsWithStats` удалить белые области площадью меньше порога.

**Роль в проекте:** убрать мусор после adaptive threshold.

**Параметр:** в итоговом ноутбуке `SMALL_AREA = 500`.

### 9.6. Лучший постпроцессинг бинаризации

**Где встречается:** PDF-отчет, `ssd_recognition_pipeline.ipynb`.

**Схема:**

1. Erosion ядром `3x3`, 1 итерация.
2. Удаление компонент меньше 500.
3. Dilation ядром `3x3`, 1 итерация.

**Результат:** небольшой прирост F1, примерно до `0.672978` для лучшей связки.

## 10. Детекция цифр и строк

### 10.1. Контурная детекция bbox цифр

**Где встречается:** `ssd_recognition_pipeline.ipynb`, генератор OCR-ноутбука.

**Идея:** после морфологии найти контуры и построить `boundingRect` вокруг каждого контура.

**Роль в проекте:** получить кандидаты на отдельные цифры.

**Плюсы:** простой и быстрый способ.

**Минусы:** плохо работает, если цифра слиплась с шумом или распалась на несколько частей.

### 10.2. Фильтр по высоте и площади

**Где встречается:** `ssd_recognition_pipeline.ipynb`, PDF-отчет.

**Идея:** оставить только bbox, размер которых похож на цифры.

**Параметры в итоговом ноутбуке:**

- `MIN_HEIGHT_RATIO = 0.05`;
- `MAX_HEIGHT_RATIO = 0.30`;
- `MIN_AREA_RATIO = 0.005`;
- `MAX_AREA_RATIO = 0.50`.

**Плюсы:** отбрасывает слишком мелкий и слишком крупный мусор.

**Минусы:** пороги зависят от масштаба и качества warp.

### 10.3. Fill ratio filter

**Где встречается:** `ssd_recognition_pipeline.ipynb`, генератор OCR-ноутбука.

**Идея:** измерить долю активных пикселей внутри bbox.

**Роль в проекте:** настоящая цифра не должна быть ни почти пустой, ни полностью заполненной.

**Параметр в итоговом ноутбуке:** допустимое заполнение `0.1 <= fill <= 0.8`.

**Плюсы:** хорошо отсекает часть мусора.

**Минусы:** сломанная бинаризация может сделать настоящую цифру слишком пустой или слишком плотной.

### 10.4. Agglomerative Clustering для строк

**Где встречается:** `ssd_recognition_pipeline.ipynb`, генератор OCR-ноутбука.

**Идея:** сгруппировать bbox по координате `y`, чтобы понять, какие цифры лежат в одной строке.

**Роль в проекте:** собрать цифры дисплея в строки давления/пульса.

**Плюсы:** не требует заранее фиксированного числа строк.

**Минусы:** чувствителен к наклону и неправильным bbox.

### 10.5. DBSCAN для строк

**Где встречается:** PDF-отчет как сравниваемый метод.

**Идея:** кластеризовать объекты по плотности.

**Роль в проекте:** альтернативная группировка цифр по строкам.

**Результат:** в топ-таблице дал тот же F1, что agglomerative и k-means для выбранной связки.

### 10.6. K-means для строк

**Где встречается:** PDF-отчет как сравниваемый метод группировки.

**Идея:** разбить bbox на кластеры по вертикальной координате.

**Минусы:** обычно нужно знать или угадывать число кластеров.

### 10.7. Фильтр перекрывающихся bbox

**Где встречается:** `ssd_recognition_pipeline.ipynb`, генератор OCR-ноутбука.

**Идея:** если соседние bbox сильно перекрываются и похожи по высоте, удалить сомнительные кандидаты.

**Роль в проекте:** уменьшить дубли и ложные области после морфологии.

### 10.8. Горизонтальные и вертикальные проекции

**Где встречается:** `screen_digit_7seg_cv.ipynb`.

**Идея:** суммировать активные пиксели по строкам и столбцам.

**Роль в проекте:** найти строки цифр по горизонтальной проекции и разделить цифры по вертикальной.

**Плюсы:** хорошо работает на чистой, ровной бинарной маске.

**Минусы:** плохо переносит наклон, шум и касание цифр с рамкой.

## 11. Распознавание цифр

### 11.1. Seven-segment recognizer

**Где встречается:** `ssd_recognition_pipeline.ipynb`, `screen_digit_7seg_cv.ipynb`.

**Идея:** каждая цифра представляется набором активных сегментов `A-G`. Алгоритм проверяет заполненность областей сегментов и выбирает наиболее похожую цифру.

**Роль в проекте:** основной классический распознаватель цифр.

**Плюсы:** не требует обучения, хорошо объясним, подходит именно для семисегментного шрифта.

**Минусы:** требует ровно вырезанной и хорошо бинаризованной цифры. Ошибается, если сегменты порваны, слиплись или bbox захватывает лишнее.

**Результат по PDF:** 18 правильных цифр из 27 сопоставленных, accuracy `0.632`.

### 11.2. Pic7Seg baseline

**Где встречается:** `create_ocr_row_comparison_notebook.work.py`.

**Идея:** существующий baseline для семисегментного распознавания, упомянутый как алгоритм из `pic.ipynb`.

**Роль в проекте:** планировался как базовая точка сравнения с Tesseract, EasyOCR и ssocr.

### 11.3. Tesseract

**Где встречается:** PDF-отчет, `create_ocr_row_comparison_notebook.work.py`.

**Идея:** универсальный OCR-движок.

**Роль в проекте:** проверялся/планировался для распознавания строк цифр.

**Вывод проекта:** без специальной настройки и дообучения плохо подходит для семисегментных дисплеев.

### 11.4. EasyOCR

**Где встречается:** PDF-отчет, `create_ocr_row_comparison_notebook.work.py`.

**Идея:** нейросетевой OCR общего назначения.

**Роль в проекте:** альтернативный OCR для строк.

**Вывод проекта:** без дообучения также плохо справляется с семисегментными цифрами.

### 11.5. SSOCR

**Где встречается:** PDF-отчет, `create_ocr_row_comparison_notebook.work.py`.

**Идея:** специализированный OCR для семисегментных дисплеев.

**Роль в проекте:** в PDF указано, что он не вошел в основную работу из-за проблем установки; генератор нового ноутбука уже предусматривает его сравнение.

**Потенциал:** это один из самых логичных кандидатов для дальнейшего сравнения, потому что он создан именно под seven-segment OCR.

## 12. Алгоритмы нормализации ориентации в OCR-ветке

### 12.1. Перебор поворотов 0, 90, 180, 270 градусов

**Где встречается:** `create_ocr_row_comparison_notebook.work.py`.

**Идея:** попробовать основные ориентации изображения и выбрать ту, где структура строк цифр выглядит наиболее правдоподобной.

**Роль в проекте:** подготовка строк перед OCR.

**Плюсы:** помогает, когда дисплей лежит на боку.

**Минусы:** не исправляет небольшой остаточный наклон.

### 12.2. Оценка residual skew

**Где встречается:** `create_ocr_row_comparison_notebook.work.py`.

## 13. Метрики и алгоритмы сопоставления

### 13.1. IoU matching

**Где встречается:** `ssd_recognition_pipeline.ipynb`, PDF-отчет.

**Идея:** предсказанный bbox или полигон сопоставляется с GT, если IoU выше порога.

**Роль в проекте:** используется для оценки дисплея и цифр.

**Пороги:** для дисплея встречаются строгие пороги `0.8` и `0.9`; для цифр в итоговом ноутбуке используется `0.5`.

### 13.2. Greedy matching по IoU

**Где встречается:** `ssd_recognition_pipeline.ipynb`.

**Идея:** собрать все пары pred/GT с IoU выше порога, отсортировать по IoU и жадно выбрать непересекающиеся пары.

**Роль в проекте:** сопоставление найденных цифр с эталонными digit-bbox.

**Плюсы:** простой способ избежать двойного назначения одной GT-цифры.

### 13.3. Precision, Recall, F1

**Где встречается:** PDF-отчет.

**Роль в проекте:** оценка бинаризации и детекции цифр.

**Ключевой смысл:** precision показывает чистоту найденных объектов, recall - полноту, F1 балансирует оба показателя.

### 13.4. Mean IoU

**Где встречается:** PDF-отчет, `ssd_recognition_pipeline.ipynb`.

**Роль в проекте:** оценка геометрического качества найденной области дисплея или цифр.

### 13.5. Accuracy распознавания

**Где встречается:** `ssd_recognition_pipeline.ipynb`, PDF-отчет.

**Идея:** среди сопоставленных цифр посчитать долю правильных предсказаний.

**Результат:** `18 / 27 = 0.632` по PDF.

### 13.6. Levenshtein distance и CER

**Где встречается:** `create_ocr_row_comparison_notebook.work.py`.

**Идея:** расстояние Левенштейна считает минимальное число вставок, удалений и замен между строками; CER нормирует это на длину GT-строки.

**Роль в проекте:** оценка OCR строк целиком.

### 13.7. ExactRowAccuracy, NonEmptyRate, LengthAccuracy

**Где встречается:** `create_ocr_row_comparison_notebook.work.py`.

**Роль в проекте:** метрики для честного сравнения OCR-методов на строках.

**Смысл:**

- `ExactRowAccuracy` - строка полностью совпала.
- `NonEmptyRate` - OCR вообще вернул непустой ответ.
- `LengthAccuracy` - OCR вернул правильное число символов.

## 14. Краткое сравнение алгоритмических веток

| Ветка | Алгоритмы | Что решает | Фактический вывод |
| --- | --- | --- | --- |
| Классический ROI | Canny, findContours, approxPolyDP, фильтр площади | Поиск дисплея | Быстро, но слишком слабо: около 30-35% TP |
| K-means ROI | K-means, connected components, crop by largest area | Безразметочный поиск области | Полезно для исследований, но нестабильно при бликах/тенях |
| Выравнивание | HoughLinesP, PCA, rotate_bound | Горизонтальная нормализация фото | Все 79 изображений обработаны, но перспективу не решает |
| Базовая YOLOv8n | COCO YOLOv8n | Быстрая проверка object detection | Находит не дисплей, а посторонние классы |
| Дообученная YOLO bbox | YOLOv8n + аугментация | Поиск дисплея bbox | Сильно лучше классики, до 87%, но bbox не учитывает поворот |
| YOLO OBB | Oriented detection | Поиск наклоненного дисплея | Лучшая основа для локализации |
| YOLO KPT | Keypoint detection | Поиск углов дисплея | В проекте слабее OBB, но полезна на некоторых сложных бликах |
| SAM2 | Prompted segmentation | Уточнение границ дисплея | Повышает mean IoU, но может снижать TP |
| Бинаризация | Adaptive Mean, Otsu, CLAHE+Otsu | Выделение цифр | Лучший путь - Adaptive Mean + контраст + постобработка |
| Морфология | Erosion, dilation, opening, closing | Очистка/склейка сегментов | Улучшает F1 умеренно, требует аккуратных параметров |
| Детекция цифр | contours, fill ratio, agglomerative clustering | bbox цифр и строки | Работает только при хорошей бинаризации |
| Распознавание | seven-segment, Tesseract, EasyOCR, ssocr | Чтение цифр | Классический seven-segment лучше универсального OCR без дообучения |

## 15. Главные алгоритмические выводы

1. Для локализации дисплея классический OpenCV-подход недостаточен: он быстрый, но плохо переносит реальные дефекты фотографий.
2. Наиболее удачная геометрическая ветка проекта - `YOLO OBB -> SAM2 -> warpPerspective`.
3. SAM2 полезен как уточнитель границ, но его результат нужно контролировать по площади, иначе возможны провалы.
4. Бинаризация - главный узкий участок после локализации. Лучшая стратегия в проекте связана с Adaptive Mean thresholding и легкой морфологической постобработкой.
5. Детекция цифр через contours и connected components работает только при чистой бинарной маске.
6. Универсальные OCR-системы не подходят для семисегментного дисплея без адаптации.
7. Классический seven-segment recognizer логичен для этой задачи, но требует качественного bbox каждой цифры.
8. Следующий сильный шаг - либо улучшать сегментацию цифр, либо обучить отдельный детектор/классификатор цифр на вырезках.
