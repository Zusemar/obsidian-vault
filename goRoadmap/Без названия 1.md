# Week 3 demos

  

Eight small programs and benchmarks, one per claim about the memory model, atomics and the

cache.

  

## Setup

  

- `go.mod` pins `go 1.27.1`. With `GOTOOLCHAIN=auto` (the default), any Go 1.21 or newer

downloads 1.27.1 on first use, so you need network once.

- If your shell exports `GOROOT`, unset it. Otherwise the build fails with

`compile: version ... does not match go tool version`.

- Run every command from this directory, the module root.

  

## Run

  

In lecture order:

  

| Demo | Command | What it shows |

|---|---|---|

| 05-falsesharing | `GOMAXPROCS=1 go run ./05-falsesharing/stats`, then `go run ./05-falsesharing/stats` | Two goroutines, each adding to its own counter, nothing shared. With the two counters side by side in one struct (`Stats`), they share a cache line; padded 64 bytes apart (`PaddedStats`), they do not. On one CPU the two take the same time. On many CPUs `Stats` gets slower than on one and `PaddedStats` faster. |

| 05-falsesharing | `go test -run=X -bench=. -benchtime=20x -count=5 -cpu=2 ./05-falsesharing` | The same effect by distance: two counters 8 to 256 bytes apart. The cost drops once they are a cache line apart. |

| 01-counter | `go run ./01-counter`, `GOMAXPROCS=1 go run ./01-counter`, `GOMAXPROCS=1 go run -race ./01-counter`, `go run -race ./01-counter` | Eight goroutines, 100,000 unsynchronised increments each, then the same with `sync.Mutex`, `atomic.Int64` and a counter owned by one goroutine. The racy version loses updates. On one CPU it usually prints the right answer, and `-race` still reports the race: a right answer does not prove the code correct. Under `-race` the program exits 66 (`go run` prints `exit status 66`): that is the demo. |

| 04-edges | `go run -race ./04-edges NN`, NN from `01` to `11` | One case per happens-before edge of the memory model: `go`, goroutine exit, channel send and receive, buffered and unbuffered, `close`, `Unlock`, `sync.Once`, atomics, a plain `bool` flag, `WaitGroup`. The race detector decides each one. Cases 02, 05 and 10 print `<-- expect race` and exit 66 by design; the other eight are clean. |

| 08-tearing | `go run ./08-tearing` | Reading a two-word value while another goroutine writes it: a `struct{a, b int}` read with `a != b`, and a string whose length belongs to one string and whose data pointer to another. Values nobody ever wrote. |

| 02-compiler | `sh 02-compiler/run.sh`, then `go run ./02-compiler` | The assembly for a plain spin loop, an atomic one and a loop over a shared variable. On amd64 the atomic load is the same `MOV` as the plain one. The plain spin loop terminates today, but the memory model does not promise it. The listing is for amd64; other architectures differ. |

| 03-reorder | `go run ./03-reorder` | The store-buffering test. With plain `int32` both goroutines sometimes read 0, an outcome sequential consistency forbids; with `atomic.Int32`, never. The count is different every run. **Do not run it under `-race`:** it reports two races and then appears to hang. |

| 06-atomiccost | `go test -run=X -bench=. -count=5 -cpu=1,2 ./06-atomiccost` | The cost ladder: plain load and store, atomic load, store, add and CAS, `Lock`+`Unlock`, then shared counters. An atomic load costs what a plain load costs; a store or a CAS is an order of magnitude more. Takes about 100 s. |

| 07-aba | `go run ./07-aba` | A lock-free stack on `atomic.Pointer`. With fresh nodes, widened window or not, or with recycled nodes alone, it stays intact. With recycled nodes and a widened window between the load and the CAS, ABA corrupts it. |

  

`01-counter` also has benchmarks of its three correct versions. Run them one `-cpu` value

per run: `go test -run=X -bench=. -benchtime=3x -count=5 -cpu=1 ./01-counter`, then the

same with `-cpu=2` and `-cpu=8`.

  

Numbers depend on the machine. Yours will differ; compare ratios, not nanoseconds.

  

All eight build on Linux and macOS.

  

## The lecture cue runner

  

`sh cues.sh` runs the lecture's demo commands in order, one key per command. `sh cues.sh

--list` prints every cue with what to expect and runs nothing; `sh cues.sh --short` keeps

the ten cues of the 60-minute deck; `sh cues.sh D4-05` runs one cue. The cue ids:

  

- D5p1, D5: `05-falsesharing/stats`, on one CPU and on all of them

- D1, D1p1, D1p1r, D1r: `01-counter`, plain, on one CPU, on one CPU under `-race`, under `-race`

- D4-01 to D4-11: `04-edges`, one cue per case

- D8: `08-tearing`

- D2a, D2: `02-compiler`, the listing, then the program

- D3: `03-reorder`

- D6: `06-atomiccost`

- D7: `07-aba`

  

The expected ranges in `cues.sh` were measured on WSL2, Intel i5-13600KF, 20 logical CPUs,

go1.27.1, on 2026-10-18, and D5p1 and D5 on 2026-10-21. They describe that machine, not

yours.
